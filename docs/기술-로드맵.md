## 지금 어디에 서 있는가

인프라는 이 규모의 팀 프로젝트에서 보기 드물게 정돈돼 있다. 블루-그린 무중단 배포, 복원 검증까지 마친 백업, Prometheus/Grafana, 그리고 실측 숫자가 들어간 부하 리포트(`docs/부하테스트-리포트.md` — 4학급 40명이 안전선)까지 갖췄다. 남은 문제는 아키텍처가 잘못 그려졌다는 종류가 아니다. **한 대짜리 인스턴스라는 전제 위에서 몇 개의 뜨거운 경로가 DB 커넥션을 쥔 채 외부 HTTP를 기다린다는 것**, 그리고 **프런트에 실패라는 상태가 거의 정의돼 있지 않다는 것** 둘이다.

이 저장소를 훑으면서 가장 자주 마주친 패턴은 따로 있다. **팀은 옳은 동작을 이미 주석과 명세에 적어 뒀는데, 배선만 빠져 있다.** `ClassroomMember.java:26`과 `V2__classroom.sql:19`는 "재가입 = 기존 행 재활성화"라고 두 번 적어 놨지만 `InviteService.java:112-118`은 그냥 새 행을 `save`한다. `TtsProvider.java:5·12`는 중복제거용 `cacheNamespace()` 훅을 만들어 뒀는데 호출부가 저장소 전체에 0건이다. `TutorActionExecutor.java:56-59`는 "PROCESSING·PREVIEW·FAILED는 아이에게 열어 줄 수 없다"고 쓰고 필터를 걸었지만, 같은 자료를 읽는 `TutorMaterialGrounding.java:54`에는 그 필터가 없다. `docs/api-spec.md:578`은 TTS 음성을 학급 멤버 전원이 재생할 수 있어야 한다고 명세해 뒀는데 코드는 학생별로 따로 만든다. `frontend/src/hooks/useTeacherPresence.ts:19-24`는 프레즌스 결함을 정확히 서술해 놓고 "그 화면들을 동시에 열지 말자"는 규약으로 피하고 있다. 이것이 이 로드맵의 항목 대부분이 effort **S**인 이유다 — 새로 설계할 것이 거의 없다.

그래서 우선순위는 단순하다. **시연에서 실제로 아이와 선생님 눈에 보일 실패부터 막는다.** 그런 실패는 백엔드가 아니라 프런트에 몰려 있다. 학교망이 5초 흔들리면 학생 화면은 "활동지 전부 완료! 🎉"를 띄우고(`useTaskStore.ts:124` → `TaskPanel.tsx:121`), 판서는 끊긴 순간에 멈춘 채로 남으며(`useScreenAnnotation.ts:141`의 의존성이 `[sessionId]` 뿐), 배포가 한 번 나가면 열어 둔 탭은 영문 에러 화면이 된다(`router.tsx` 전체에 `errorElement` 0건). 백엔드 쪽 항목들은 대부분 지금 당장 시연을 깨뜨리지는 않는, 학기 운영으로 넘어갈 때 값을 하는 것들이다. 아래 표에서 **체감**과 **내부**를 구분해 둔 이유가 이것이다.

## 운영 실제 상태와 대조 (저장소만으로는 알 수 없는 것)

이 로드맵은 저장소 코드를 근거로 작성한 뒤, 운영 인스턴스에서 직접 확인해 세 가지를
보정했다. **저장소에 기본값이 있다는 것과 운영이 그 기본값을 쓴다는 것은 다른 이야기다.**

| 항목 | 저장소 기준 판단 | 운영 실측 | 보정 |
|---|---|---|---|
| JWT 시크릿 | `application.yml:31` 기본값 `mallang-local-dev-secret-...` 로 조용히 부팅 | **`JWT_SECRET` 주입되어 있음** — 기본값 미사용 | 지금 뚫려 있는 상태가 **아니다.** 다만 값이 빠지면 조용히 기본값으로 뜨는 구조는 그대로이므로, 항목의 취지는 "부팅 실패시키기(fail-fast)"로 축소한다 |
| 스프링 프로필 | 저장소에 `SPRING_PROFILES_ACTIVE` 흔적이 없어 `local` 로 뜰 것 | **주입되어 있음** | "프로필 게이트를 신뢰할 수 없다"는 근거가 약해진다. 다만 값 비교 방식이 더 견고하다는 결론 자체는 유지 |
| Swagger 공개 | 운영 도메인에 무인증 노출 추정 | **`/swagger-ui/index.html` 200, `/v3/api-docs` 200 — 실제로 열려 있음** | 확인됨. 그대로 유효 |

교훈이 하나 더 있다. **`.env` 로 주입되는 값은 저장소를 아무리 읽어도 보이지 않는다.**
설정 관련 지적을 할 때는 실행 중인 컨테이너의 환경변수를 함께 확인해야 한다.

## 1. 시연 전에 할 것

### 1군 — 반드시

#### 1-1. 학생 화면에서 API 실패가 "다 했음"으로 보인다 · 체감 · S

`useTaskStore.ts:122-124`의 catch가 이렇게 끝난다.

```ts
} catch {
  // 권한/네트워크 오류 — 없는 과제를 만들어내지 않고 빈 목록으로 둔다
  if (seq === loadSeq) set({ tasks: [], loaded: true })
}
```

빈 목록으로 두는 판단 자체는 방어적이지만, 그 빈 목록을 받는 화면이 `TaskPanel.tsx:121`이다. `doneCount >= tasks.length`가 `0 >= 0`으로 참이 되어 **"활동지 전부 완료! 🎉"** 가 뜬다. 선생님이 낸 과제를 못 본 아이가 칭찬 문구를 본다. `QuizView.tsx:151`도 같은 모양이라 실패 시 `setQuestions([])` → `:196` "아직 풀 수 있는 문제가 없어요"가 된다.

더 나쁜 건 회복 경로가 없다는 점이다. 저장소 전체에 `navigator.onLine` / `online` / `visibilitychange` 처리가 0건이고, 목록을 다시 부르는 경로는 `ClassroomPage.tsx`의 `ASSIGNMENT_PUBLISHED` 이벤트 하나뿐이다 — **교사가 새 과제를 또 공개해야만 복구된다.** 그 수업 내내 빈 화면이라는 뜻이다.

바꿀 것: 스토어에 `error: string | null`을 추가해 catch에서 `tasks`를 비우지 말고 error만 세운다(이전 목록 유지). 화면은 error일 때 "인터넷이 잠깐 느려요 / 다시 받아올게요" + 큰 버튼 하나를 그리고, `online`·`visibilitychange`에서 `load(classroomId)`를 한 번 다시 부른다. 완료 문구는 `tasks.length > 0`일 때만 낸다.

왜 1순위인가: 시연장 와이파이가 한 번 흔들리는 것만으로 재현되고, 재현되면 시연의 핵심 서사("선생님이 낸 과제를 아이가 푼다")가 그대로 깨진다. 서버 부하는 0이고 스토어 필드 하나 + 화면 분기다.

#### 1-2. 배포·청크 실패 시 흰 화면 · 체감 · S

`Jenkinsfile:205`가 `rsync -a --delete frontend/dist/ /var/www/mallang/`로 옛 자산을 지운다. 그런데 `lazyPages.ts`는 페이지 13개를, `ModalHost.tsx:14-56`은 모달 9개를 전부 `lazy()`로 받는다. 배포 전에 탭을 열어 둔 사람이 그 뒤 처음 여는 화면의 청크를 요청하면 404 → dynamic import reject → 트리 언마운트다.

그런데 `router.tsx:33-71` 전체에 `errorElement`가 0건이고, `frontend/src` 어디에도 `ErrorBoundary`/`componentDidCatch`/`vite:preloadError` 처리가 없다(직접 grep, 무출력). react-router 7.18의 기본 에러 경계가 잡아 주긴 하지만 결과는 영문 "Unexpected Application Error!" 화면이다. 저학년에게는 백지와 같고, 어느 쪽이든 **다시 시도할 버튼이 없다.**

바꿀 것: 공용 `lazyWithRetry(loader)`로 두 파일의 `lazy()`를 감싼다(300ms 뒤 1회 재시도, 그래도 실패하면 `sessionStorage` 플래그로 1회만 `location.reload()`). 그리고 최상위 라우트에 `errorElement`를 달아 `RouteFallback`과 같은 톤의 화면 + 큰 버튼 하나를 둔다.

왜 1순위인가: QA 기간에 배포가 잦고, 학교망에서는 배포 없이도 청크 요청 한 번 실패로 같은 결과가 난다. 파일 3개, 상시 CPU 0.

#### 1-3. 재접속 후 판서·교사 채팅이 재동기화되지 않는다 · 체감 · S

`useClassroomSocket.ts`의 스냅샷 effect는 의존성이 `[sessionId, status, ...]`(`:225`)라 재접속마다 다시 돈다. 그런데 그 effect가 복원하는 것은 손들기·판서권한·음소거·잠금뿐이고 **`boardStrokes`는 손도 대지 않는다.** 판서 복원은 `useScreenAnnotation.ts:125-141`의 별도 effect인데 의존성이 `[sessionId]` 하나라 재접속에 반응하지 않는다. 캔버스를 얹는 컴포넌트도 재접속으로 언마운트되지 않고, 브로커는 `enableSimpleBroker`(`WebSocketConfig.java:31`)라 재전송이 없다.

결과: 절전 복귀·AP 로밍으로 5초만 끊겨도 그 사이의 획과 `BOARD_CLEAR`가 학생 캔버스에 영영 반영되지 않는다. "지웠는데 남아 있는 칠판", "앞부분이 빠진 그림"이 되고, 저학년은 이걸 자기 화면 고장으로 신고하지 못한다. 교사 채팅 패널도 같은 이유로 끊긴 동안 온 질문이 새로고침 전까지 안 뜬다.

바꿀 것: `ClassroomSocket.ts:84-86`의 `onConnected`가 지금 `loadRoster`만 부르는데(주석: "재접속 때마다 명단을 다시 맞춘다") 여기에 재접속 카운터를 하나 올리고, `useScreenAnnotation`과 `LiveChatPanel`의 의존성 배열에 그 값을 넣는다. `ScreenAnnotator.replaceAll`은 멱등이고 채팅에는 이미 중복 제거가 있어 부작용이 없다. **단, 드래그 중에 `replaceAll`이 돌면 진행 중인 획이 빠지므로 `current === null`일 때만 재동기화하는 가드 한 줄을 넣을 것.**

왜 1순위인가: 판서는 시연의 중심 화면이고, 재접속은 학교망에서 예외가 아니라 기본값이다. 이미 있는 훅(`onConnected`)에 값 하나를 태우는 일이다.

#### 1-4. 말랑이 답변에 요약 LLM 왕복이 직렬로 붙는다 · 체감 · S

`AiTutorService`의 흐름이 `:101` `tutorClient.ask(...)` → `:107` `record(...)` → `:110-112` `if (answeredBy == LLM) updateMemory(...)` → `:113` `return`이다. `updateMemory`(`:190`)는 `:192`에서 `tutorClient.summarize(...)`를 부르고, 그게 **두 번째 LLM 왕복**이다. 컨트롤러도 완전 동기다.

주석과 코드가 어긋나 있다는 점이 이 항목의 핵심이다. `AiTutorService` 안의 주석은 요약 갱신을 "베스트에포트"라고 규정하며 "답은 이미 학생에게 나갔으므로 여기서 예외를 밖으로 던지지 않는다"고 적어 뒀지만, 실제로는 예외만 삼킬 뿐 **지연은 그대로 아이에게 전가된다.**

절약폭은 정직하게 적는다. 같은 저장소가 GMS 왕복을 실측해 뒀다 — `ReportCommentCache.java:19-20` "운영에서 1.07~1.88초로 측정됐고(2026-08-03)". 요약 호출은 `max_tokens` 200으로 답변(500)보다 짧으니 평상시 절약은 **1~2초**다. "두 배"가 아니다. 다만 `AiTutorClient.java:34`의 `READ_TIMEOUT = 20초`가 두 번 걸리면 최악 40초이고, 게이트웨이가 느려질 때 가장 먼저 티가 나는 곳이 시연 화면이다.

바꿀 것: `updateMemory`를 별도 빈(`TutorMemoryUpdater`)으로 빼고 `@Async`를 붙인다. **같은 클래스의 private 메서드를 그대로 `@Async` 붙여 봐야 자기호출이라 프록시를 안 탄다 — 반드시 다른 빈으로 분리해야 한다.** `@EnableAsync`는 이미 걸려 있어 새 인프라가 없다.

주의(제안에 빠져 있던 것): `V18__ai_tutor_memory.sql:20`에 `uq_ai_tutor_memory(classroom_id, student_id)` 유니크가 있고 `updateMemory`는 find-or-create다. 비동기로 빼면 같은 학생의 연속 질문 두 건이 동시에 insert를 시도할 창이 넓어진다. 예외를 삼키므로 조용히 요약 한 번이 유실되는 선에서 끝나지만, **risk는 "낮음"이 아니라 "중간"으로 보고 `AiTutorServiceTest`의 `summarize` 검증 3곳(`:242·268·279`)을 `verify(timeout)` 형태로 손봐야 한다.** 실행기는 `AsyncConfig`의 `taskExecutor`(core 2/max 4/queue 50)를 쓰되, 이 풀은 지금 PDF 추출과 공유한다는 것(`AsyncConfig.java:11` 주석)을 감안해 큐를 넉넉히 두거나 전용 풀을 하나 더 둔다.

#### 1-5. 강퇴·탈퇴 후 재초대 수락이 500 · 체감 · S

이건 `docs/트러블슈팅.md`가 "관통하는 패턴"으로 이미 규정한 그 구조가 손대지 않은 채 남아 있는 사례다. `ClassroomMember.java:32-33`이 `@SQLDelete` + `@SQLRestriction("deleted_at is null")`이고, DB 제약은 `V2__classroom.sql:22`의 전 행 `uq_classroom_member UNIQUE (classroom_id, user_id)`다. V16/V17이 `classroom.alias`만 부분 유니크로 바꿨고 `classroom_member`는 마이그레이션 전체에서 손대지 않았다.

특이한 점은 **팀이 올바른 동작을 두 곳에 적어 놨다는 것**이다.

- `ClassroomMember.java:26` — "강퇴 = soft delete, 재가입 = 기존 행 재활성화 (UNIQUE(classroom_id, user_id) 때문)"
- `V2__classroom.sql:19` — "강퇴 = soft delete. 재가입은 기존 행 재활성화 (UNIQUE 제약 때문)"

그런데 `InviteService.java:112-118`은 `@SQLRestriction`이 걸린 `findByClassroomIdAndUserId`로만 확인하고 없으면 `save`한다. 삭제된 행은 조회에서 안 보이고 DB는 차 있으니, 제외했던 동료 선생님을 다시 초대하면 수락 순간 유니크 위반이다.

바꿀 것: `ClassroomMember`에 `restore(role)`을 더하고, `acceptAsTeacher`가 삭제된 행까지 보는 네이티브 조회로 기존 행을 찾아 되살린다(`UserRepository`가 `existsByUsernameIncludingDeleted`로 이미 쓰는 패턴). 함께 `GlobalExceptionHandler`에 `DataIntegrityViolationException → 409` 핸들러를 넣는다 — 이 파일은 지금 전체 43줄에 핸들러가 둘뿐이고 백엔드에 `@RestControllerAdvice`가 이 하나뿐이라, 같은 구멍이 열려 있는 `uq_team_member_classroom_user`·`uq_submission`·`invite.code`까지 한 번에 덮인다.

과장하지 않기: 사용자 화면에 괴상한 문구가 뜨지는 않는다. `frontend/src/lib/apiError.ts`가 500대를 "서버에 문제가 생겼어요"로 뭉개 준다. 그리고 학생 경로에는 이 버그가 없다 — `acceptAsStudent`는 매번 새 User를 만들어 (classroom_id, user_id) 쌍이 항상 새롭다. **선생님 전용 결함**이라 impact는 medium이다. 그럼에도 1군인 이유는 QA와 시연 준비에서 "잘못 뺐다가 다시 넣기"가 매우 흔한 조작이고, 수정이 스키마를 건드리지 않아 반나절이기 때문이다.

#### 1-6. 교사 답장이 학급을 검증하지 않는다 · 체감 · S(슬라이스)

`PresenceService.java:96-102`의 `anyFreeTeacher()`는 주석이 스스로 "라우팅 규칙 2: 온라인이면서 어느 팀 룸에도 없는 선생님 1명 **(학급 무관)**"이라고 적어 뒀고, 근거가 되는 SET(`:19-20`)에는 학급·세션 접두어가 없다. `WebSocketEventListener`가 STOMP 접속만으로 채워 넣으므로 **다른 반 담임이 로그인만 해 둬도 후보가 된다.** 그리고 `ChatRouterService.java:78-89`의 `routeTeacherReply`는 Redis 배정 쌍만 확인하고 학급 구성원 여부를 보지 않아 답장까지 정상 처리된다.

지금이 정확히 그 조건이다 — QA 중 팀원 5명이 각자 교사로 로그인한다. 두 계정만 동시에 켜져 있으면 A반 아이가 쓴 질문 원문이 B반 담임에게 가고, 정작 A반 담임 화면에는 안 뜬다.

**전면 개편은 시연 전 범위가 아니다(→ 2절 19번).** 시연 전에는 `routeTeacherReply`에 학급 구성원 검증 한 줄만 넣는다. `SessionService`가 이미 쓰는 `findUserIdsByClassroomIdAndRoleIn(classroomId, [OWNER, MAINTAINER])`을 그대로 재사용하면 3줄이고, 명세 v0.6의 라우팅 규칙과 충돌하지 않으며, "아이 질문이 남의 반 선생님에게 배달된 뒤 답장까지 오가는" 최악의 절반을 즉시 막는다.

### 2군 — 손이 남으면

#### 1-7. TTS 합성이 `@Transactional` 안에서 30초를 잡는다 · 체감(간접) · S

`TtsService.java:47`에 `@Transactional`이 붙어 있고, 그 안에서 `:56` 외부 HTTP → `:64` 파일 쓰기 → `:67`에야 `save`다. `GmsTtsProvider.java:31`의 타임아웃은 30초. `application.yml`에는 hikari 설정도 `provider_disables_autocommit`도 없어서, Hibernate가 트랜잭션 begin 시점에 물리 커넥션을 즉시 잡고 30초를 그대로 쥔다. 풀은 기본 10이다. 동시 10명이면 풀이 마르고 그 순간 로그인·제출·수업 상태 조회까지 전부 멈춘다.

같은 저장소에 정답이 이미 있다. `ReportService.java:28-32`, `SubmissionService.java:74-77`이 "LLM 왕복을 트랜잭션에 끌어들이지 않는다"는 3단 분리를 하고 있고, `AiTutorService`의 `record()`도 트랜잭션 밖에서 `getReferenceById` + `save`를 그대로 해서 프록시 문제가 없음이 확인된다. `synthesize()`에서 `@Transactional`만 떼고 같은 모양으로 나누면 된다.

과장하지 않기: 프런트가 이미 문항별로 캐시한다(`QuizView.tsx:19` "같은 문항을 다시 눌러도 서버를 또 부르지 않게 캐시한다"). "저학년이 다시 눌러 수백 건이 몰린다"는 증폭은 한 화면 안에서는 일어나지 않는다. 그래서 1군이 아니라 2군이다. 다만 커넥션 30초 점유는 추정이 아니라 실제이므로, 손이 남으면 반나절짜리로 먼저 집어 갈 만하다.

#### 1-8. 말랑이가 미확인(PREVIEW) 자료를 근거로 쓴다 · 체감·안전 · S

`TutorMaterialGrounding.java:54`가 `materialRepository.findByClassroomId(classroomId)`를 상태 필터 없이 돌고, `MaterialRepository`는 상태 무관 메서드 하나뿐이다(파일 전체 13줄). 바로 옆의 `TutorActionExecutor.java:60-62`는 같은 쿼리에 `.filter(m -> m.getStatus() == READY)`를 걸어 두고 주석까지 달아 놨다 — "PROCESSING·PREVIEW·FAILED는 선생님이 확인을 마치지 않은 자료라 아이에게 열어 줄 수 없다". 목록에는 필터가 있고, **본문을 답변 근거로 싣는 쪽에는 없다.**

노출 범위는 증거가 말하는 것보다 좁다. PROCESSING은 `extractedText`가 아직 null이라 `:55-58`에서 걸러지고, FAILED도 텍스트를 쓰기 전에 실패하므로 null이다. **실제로 새는 상태는 PREVIEW 하나뿐이다.** 그런데 PREVIEW야말로 "선생님이 아직 확인 안 했고, 잘못 올렸으면 곧 지울" 바로 그 상태다. 복식학급이라 한 교실에 여러 학년 자료가 섞여 올라가는 것이 기본값이라는 점을 감안하면 게이트 우회의 실질은 남는다.

바꿀 것: `MaterialRepository`에 `findReadyByClassroomId`를 추가하고 두 호출부가 그것을 쓰게 한다(후자는 스트림 필터를 지운다). 같은 김에 grounding 쪽은 `title`·`extractedText`만 뽑는 프로젝션으로 바꾼다 — `SubmissionRepository`가 jsonb를 피하려고 쓴 것과 같은 수법이다. 3개 파일, 20줄 안쪽.

#### 1-9. 기본 JWT 시크릿으로 조용히 부팅한다 · 내부 · S

`application.yml:31`에 `secret: ${JWT_SECRET:mallang-local-dev-secret-key-change-me-32bytes!}`가 커밋돼 있다. `JwtTokenProvider`의 생성자(`:32-39`)에는 기동 검사가 없다. 운영 `.env`에서 `JWT_SECRET`이 빠지거나 오타가 나면 서비스는 아무 이상 없이 뜨고, 그 순간 누구나 공개된 문자열로 `role=TEACHER` 토큰을 서명할 수 있다. **실패가 조용해서 아무도 모른다는 것이 이 항목의 값어치다.**

바꿀 것은 딱 한 가지 조건이다: **커밋된 기본값과 문자열이 같으면 기동 중단.** 제안으로 나왔던 "prod 프로필에서만 검사"는 이 저장소에서 작동을 보장할 수 없다 — `SPRING_PROFILES_ACTIVE`가 저장소 어디에도 없고 `application.yml:5`의 기본 프로필이 `local`이라, 운영이 local로 뜨고 있으면 가드가 영원히 발동하지 않는다. "32바이트 미만" 검사도 불필요하다 — `Keys.hmacShaKeyFor`(`JwtTokenProvider.java:36`)가 이미 `WeakKeyException`으로 막는다.

LiveKit 시크릿은 같이 묶지 않는다. `infra/server/docker-compose.yml:68-69`가 같은 `.env`에서 `LIVEKIT_KEYS`를 조립하므로, 빠지면 화상 수업이 눈에 띄게 깨진다 — 조용한 실패가 아니다.

적용 순서: 서버에서 `grep JWT_SECRET .../infra/server/.env`로 값이 실제로 있는지 먼저 확인하고, 없으면 값을 넣은 다음 가드를 배포한다. 블루-그린이라 새 슬롯 헬스체크에서 걸리면 전환되지 않으므로 잘못된 배포는 전환 전에 막힌다.

#### 1-10. Swagger UI가 운영 도메인에 무인증 공개 · 내부 · S

`SecurityConfig.java:49`가 `/swagger-ui/**`, `/v3/api-docs/**`를 `permitAll`이고, nginx의 두 location(`infra/server/nginx/sites-available/default:139-151`, 주석이 "Swagger (개발 기간 동안 팀 공유용)")에 `allow`/`deny`도 `auth_basic`도 없다. springdoc은 실제 의존성이라 문서가 살아 있다.

모든 엔드포인트는 여전히 인증되므로 실제 손해는 API 표면 노출 그 자체다 — impact low. 그래도 미성년자 데이터를 다루는 서비스가 공개 도메인에 API 지도를 걸어 두는 그림은 심사에서 설명하기 어렵다. nginx 두 블록에 `auth_basic` 또는 팀 IP allow/deny 두 줄이면 끝난다.

**저장소의 nginx 파일은 호스트 사본이다.** 업스트림 전환 conf는 EC2 호스트에만 있으므로, 서버의 `/etc/nginx`에서 직접 고치고 `nginx -t` 후 reload해야 실제로 적용된다. `springdoc.api-docs.enabled: false`를 prod 프로필에 거는 대안은 위 1-9와 같은 이유로 쓰지 않는다.

#### 1-11. 제출 실패 시 답안이 통째로 사라진다 · 체감 · M(부분만 S)

impact를 medium으로 둔 이유: 제출 순간이라는 좁은 창에서만 발생하고, 완료로 잘못 칠하지는 않으며(`closeCelebrate`가 `result`가 null이면 `completeTask`를 안 부른다), 사유 문구도 토스트로는 한 번 나온다.

## 2. 시연 후

#### 2-13. 아이의 위험 신호가 교사에게 전달되지 않는다 · 체감·안전 · M

**시연 이후 목록에서 가장 중요한 항목이다.** `TutorSafetyFilter`의 `BANNED`는 전부 욕설·비속어이고, 클래스 주석이 명시적으로 "폭력·성적·자해 같은 뉘앙스가 필요한 주제는 여기서 단어로 막지 않는다 — `AiTutorClient`의 시스템 프롬프트에 맡긴다"고 적어 뒀다. 그 프롬프트는 아이에게 "믿을 수 있는 어른과 나눠 줘"라고 말하지만, **어른에게 알리는 코드 경로가 저장소에 존재하지 않는다.** `AnsweredBy`는 `LLM/TEMPLATE/BLOCKED` 셋뿐이라 "살펴봐야 할 대화"라는 개념 자체가 없고, 교사 노출은 학생 상세의 읽기 전용 목록뿐이다.

복식학급은 교사 한 명이 여러 학년을 동시에 본다. 담임이 20명의 말랑이 대화를 매일 훑어보는 건 비현실적이다.

바꿀 것: `TutorSafetyFilter`에 차단과 분리된 두 번째 목록(자해·폭력 피해·괴롭힘 신호)을 두고, 걸리면 **답변은 정상적으로 내보내되** `ai_tutor_message`에 `flagged` + 사유를 남기는 마이그레이션(V21)을 넣는다. 교사 화면에는 학생 목록 배지 하나.

**구현 시 주의 — 원안 그대로 하면 안 된다.** 원안은 알림을 `TutorActionExecutor.askTeacher`가 쓰는 `DirectChatService.send`로 보내자고 했는데, 그 메서드는 `sender = 학생`으로 저장한다. 아이가 보내지 않은 말이 자기 이름으로 담임에게 간 것처럼 남고, 하필 아이가 털어놓은 내용이라 "아이 경험은 그대로"라는 전제가 무너진다. **flagged 컬럼 + 교사 쪽 전용 표시까지만 한다.**

왜 시연 후인가: 마이그레이션 + 엔티티/필터/DTO + 프런트 배지로 확실히 M이고, 시연 D-2에 스키마를 건드릴 이유가 없다. 다만 학교 도입·학부모 설명에서 가장 먼저 물어보는 지점이므로 **시연 직후 첫 항목으로 잡을 것.**

#### 2-14. TTS 중복 합성·무한 누적 · 내부 · M

`TtsService.java:58`이 매 요청 랜덤 UUID로 새 `storage_key`를 만들고 `:67-69`에서 새 행을 만든다. 같은 텍스트를 조회하는 코드가 없고, `UploadedFileRepository`는 8줄짜리 빈 인터페이스다. 지우는 경로도 없다 — 백엔드 전체에 `uploaded_file` delete가 0건, `@Scheduled`도 0건. 학급을 삭제해도 자료를 지워도 남는다.

여기서도 배선만 빠져 있다. `TtsProvider.java:5·12`가 `cacheNamespace()`를 "중복제거 키에 섞여, provider/모델/음성이 바뀌면 다른 파일로 취급되게 한다"고 정의해 두고 구현 2개를 갖췄는데, **호출부가 저장소 전체에 0건이다.** 그리고 `docs/api-spec.md:578`이 "공개된 과제의 content에 참조된 파일(TTS 음성 등) → 해당 학급 멤버 전원"을 이미 권한 정책으로 못 박아 뒀다 — TTS_AUDIO에 한해 소유자 검사를 면제하는 것은 새 보안 결정이 아니라 **명세 이행**이다.

바꿀 것: `storage_key`를 `sha256(cacheNamespace + voice + text)`로 잡고, 합성 전에 그 키로 조회해 있으면 재사용한다(`V7__uploaded_file.sql:10`의 `storage_key UNIQUE`가 그대로 중복 방지 장치가 된다). 권한은 `FilePurpose.TTS_AUDIO` 한정 예외로 — **RECORDING(학생 녹음)까지 열면 안 된다.** 그리고 `purpose`·`created_at` 인덱스 + 기존 백업 크론 옆에 N일 정리 잡.

정정 두 가지: 원안의 "storage_key는 공유하되 행은 학생별로"는 `storage_key UNIQUE`와 양립하지 않는다. 실행 가능한 건 단일 행 공유 + 권한 예외뿐이다. 그리고 "GMS 크레딧 25배"는 저장소에서 확인할 수 없다 — `application.yml:83`의 `provider` 기본값이 `stub`이고 infra 어디에도 `TTS_PROVIDER` 설정이 없다. 지연·디스크 누적 이득은 provider와 무관하게 남는다.

#### 2-15. 비전 OCR이 트랜잭션을 쥔 채 최대 30회 LLM 호출 · 내부 · S

`MaterialExtractionService.java:41-43`에 `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)`가 겹쳐 있고, 그 안에서 `extract` → `promoteToVision` → `VisionTextExtractor.extract`가 페이지 루프를 돈다. 트랜잭션이 필요한 이유는 상태 변경 더티체킹 한 줄뿐인데, 커밋은 페이지 루프가 끝나야 일어난다. `provider_disables_autocommit`이 없으므로 커넥션은 begin 시점부터 붙잡힌다.

바꿀 것: 리스너에서 `@Transactional`을 떼고 ① 짧은 읽기로 `storageKey`만 → ② 트랜잭션 밖에서 추출 → ③ `@Modifying` 업데이트로 결과만 쓴다. `SubmissionRepository.java:56-63`의 `updateFeedback`이 정확히 이 목적("호출 지점이 트랜잭션 밖이라 더티 체킹을 쓸 수 없어")으로 이미 있다. 단, `previewReady`는 4칼럼, `fail`은 2칼럼을 쓰므로 **업데이트 메서드는 하나가 아니라 두 개**가 필요하다.

과장하지 않기: 이 리스너는 `AsyncConfig`의 core 2/max 4에서 도니 최악에도 풀 10 중 4개까지다. "30페이지 × 60초 = 30분"은 모든 페이지가 타임아웃해야 나오는 수치고, 2단계는 1단계가 SPARSE로 판정된 스캔본에만 탄다. 그래서 내부 품질 항목이고 시연 후다.

**페이지 전사 병렬화는 채택하지 말 것.** `transcribe`는 HTTP 왕복만이 아니라 150 DPI PDF 렌더링(CPU)을 포함한다. 지속 기준선 0.9 vCPU인 버스터블에서 백엔드·LiveKit·Postgres와 코어를 다툰다.

#### 2-16. 수업 이력 조회가 화이트보드 JSONB를 통째로 읽는다 · 내부 · S

`LiveSessionRepository.java:28`의 주석이 문제를 스스로 인정한다 — "boardSnapshot(jsonb)은 목록에서 안 쓰지만 엔티티 컬럼이라 함께 온다". `LiveSession`의 `boardSnapshot`은 `@JdbcTypeCode(SqlTypes.JSON) String`이라 지연 로딩이 안 걸리므로, 프로젝션이 실제로 옳은 처방이다.

증폭은 코드로 확인된다. `SessionAttendanceService`의 출석 조회는 (classroomId, studentId) 단위라 **학생 한 명을 열 때마다 학급 전 수업 이력을 다시 읽는다.** 선생님이 25명을 훑으면 같은 스냅샷을 25번 왕복시킨다. `ActivityFeedService`는 시작·종료 시각 두 개를 뽑으려고 같은 것을 읽는다.

세 호출부가 쓰는 필드가 `id·classroomId·startedByName·startedAt·endedAt` 뿐이므로 스칼라 프로젝션 쿼리 하나 + 인터페이스 프로젝션을 더하고, 엔티티 메서드는 스냅샷이 실제로 필요한 detail 경로만 남긴다.

강도는 낮춰 적는다. 스냅샷은 세션 종료 시 획이 있을 때만 채워지고, 같은 리포지토리 주석(`:29`)이 "학급당 수업 수가 학기 단위로도 수십 건"이라고 규모를 밝혀 뒀다. "GC 부담으로 직결"은 측정 근거가 없는 수사다.

#### 2-17. 학습자료 텍스트를 상한 없이 LLM에 싣는다 · 내부 · M

두 갈래다.

**(a) 튜터 경로 — 진짜 S.** `TutorMaterialGrounding.contextFor`와 `TutorActionExecutor.offerableMaterials`가 같은 `findByClassroomId`를 연달아 두 번 돌린다. `Material.extractedText`는 `@Column(columnDefinition="text")` 일반 필드라 지연 로딩이 아니어서 **질문 하나당 학급 자료 전문이 두 벌 JVM으로 올라온다.** 그런데 후자는 `id`·`title`만 쓴다. `select new MaterialRef(m.id, m.title)` 투영 쿼리 하나면 끝난다. 위 1-8과 같은 파일을 건드리므로 **묶어서 처리하는 편이 낫다.**

**(b) 과제 생성 경로 — M.** `MaterialSource`가 `getExtractedText()`를 무절단으로 프롬프트에 붙이고, `AssignmentDtos`의 `materialIds`는 `@NotEmpty`만 있을 뿐 개수·글자 상한이 없다. 스캔 학습지 두세 개면 입력 토큰이 수만~십수만이 되고, 컨텍스트 한계를 넘으면 게이트웨이 400이 `GenerationJobRunner`의 catch를 타고 `job.error`에 원본 응답 문자열째 실려 교사 화면에 뜬다. 시연 전이라면 **단순 상한(자료당 8k, 합계 20k)으로 시작**하고, "문단 균등 샘플링 + 잘림 안내를 초안에 실어 교사에게 노출"은 백엔드 샘플링 + 초안 스키마 + 프런트까지 건드리므로 시연 후로 미룬다.

#### 2-18. 교사 프레즌스가 userId SET 하나 · 체감 · S

`PresenceService.java:19`의 `presence:online:teachers`는 TTL 없는 전역 SET이고, `WebSocketEventListener`가 CONNECT/DISCONNECT에서 무조건 SADD/SREM한다. 그래서 선생님이 라이브 화면과 채팅 인박스를 두 탭으로 열었다가 하나만 닫아도 완전히 오프라인이 된다.

**팀은 이미 이 결함을 알고 있고, 고치는 대신 규약으로 피하고 있다.** `frontend/src/hooks/useTeacherPresence.ts:19-24`가 "백엔드 프레즌스는 STOMP 세션별 refcount가 아니라 teacherId 단순 Set이라 소켓을 둘 열면 하나만 닫혀도 완전히 오프라인 처리된다"고 경고하고, 소켓을 여는 화면 3곳을 동시에 열지 말라고 적어 뒀다. 라우트가 배타적이라 한 탭 안에서는 안전하므로 남는 위험은 두 탭뿐이다 — 실재하지만 좁다.

바꿀 것: CONNECT 시 `SADD presence:teacher:{id}:conns {stompSessionId}`, DISCONNECT 시 `SCARD == 0`일 때만 online에서 뺀다. 강제 종료 후 유령 id는 **`ApplicationReadyEvent`에서 DEL하지 말 것** — 블루-그린 20초 중첩 동안 구 슬롯에 붙어 있던 교사가 지워진다. `conns` 키에 TTL을 주는 편이 안전하다. (유령의 절반은 자가 치유된다. SET에 담기는 값이 userId라 3초 뒤 재접속하면 같은 id가 다시 들어간다.)

#### 2-19. 채팅 라우팅을 학급 단위로 좁히기 · 체감 · **L** · 팀 합의 선행

impact는 이 목록에서 가장 높지만 **effort L이고, 시연 전에는 못 한다. 못 하는 건 못 한다.** 이유를 그대로 적는다.

- `ChatRouterService.java:94-97`이 명시적으로 못 박아 뒀다 — "…팀 결정이다. **버그가 아니므로 while 루프를 단건 pop으로 바꾸지 말 것 (`ChatRouterServiceTest`가 고정)**".
- `PresenceService.java:95`는 "학급 무관"을 **명세 v0.6의 라우팅 규칙 2**로 규정한다.
- 대기열 키를 `chat:waiting:{sessionId}`로 바꾸는 것은 Redis 스키마 변경이다. 배포 시점에 대기 중인 학생이 있으면 그 항목이 유실되므로 수업이 없는 시간에 배포해야 한다.
- `ChatRouterServiceTest`가 `anyFreeTeacher`를 5곳에서 목킹한다.

즉 이건 코드 수정이 아니라 **명세 개정 + 팀 합의 + 테스트 재작성**이다. 순서는 ① "학급 무관이 정말 의도인가"를 팀이 먼저 결론 내고 → ② `anyFreeTeacher(classroomId)`로 시그니처를 바꿔 학급 교사와 교집합 → ③ 대기열 키를 세션 단위로 → ④ `drainWaitingQueue`는 `lastSessionOfTeacher`로 그 수업 대기열만 비운다. ③④를 하면 `onSessionEnded`의 "pending 맨 뒤가 이 세션 것인지"라는 취약한 추정 로직이 통째로 사라지는 것이 덤이다.

시연 전 슬라이스(1-6)를 이미 넣어 뒀으므로, 여기서 서두를 이유가 없다.

## 4. 지금은 하지 말 것

흔히 하고 싶어지지만, 이 규모와 이 제약(4코어 한 대, 학생 5명, 시연 임박)에서는 역효과다.

**마이크로서비스 분리 / 쿠버네티스.** 백엔드 189파일 14,351줄이고 도메인 경계가 이미 패키지로 깔끔하게 나뉘어 있다. 쪼갤 이유가 있는 규모가 아니고, 무엇보다 **인스턴스를 늘릴 수 없다.** 같은 4코어에 컨트롤 플레인을 얹으면 지속 기준선 0.9 vCPU를 상시로 갉아먹는다. 지금 블루-그린 무중단 배포가 이미 돌고 있다.

**다중 인스턴스 + 외부 STOMP 브로커(RabbitMQ 등).** `docs/architecture.md`가 "현재 백엔드는 단일 인스턴스 + Spring STOMP simple broker. 다중 인스턴스 전환 시 RabbitMQ 등 외부 broker relay 도입"이라고 이미 판단을 적어 뒀다. 전환 시점이 지금이 아니다. 그리고 이 로드맵의 프레즌스·라우팅 항목(18·19)은 **전부 "단일 인스턴스"를 전제로 훨씬 싸게 풀린다** — 다중 인스턴스로 가면 그 전제가 무너져 난이도가 한 단계 올라간다.

**pgvector 임베딩 RAG.** 이미지에는 확장이 들어 있지만(`infra/server/docker-compose.yml:18` `pgvector/pgvector:pg16`) 마이그레이션 V1~V20 어디에도 `CREATE EXTENSION`이 없고, `docs/api-spec.md:832`에 팀이 "자료가 학기 단위로 쌓인 후 MATERIAL_CHUNK + 임베딩으로 확장, 현재는 full-context 주입"이라고 유예 판단을 적어 뒀다. 청킹·인덱싱·재색인까지 L이고, 실제로 아픈 부분(2-17의 투영 쿼리와 단순 상한)은 반나절에 사라진다.

**전면적인 Redis 캐시 계층 도입.** 이 저장소는 이미 필요한 자리에 정확히 캐시를 두고 있다 — `ReportCommentCache`가 "키에 강·약점의 지문을 넣는 것이 곧 무효화"라는, 무효화 문제를 아예 없애는 설계로 돌아간다. 여기에 범용 캐시 어노테이션을 흩뿌리면 무효화 지점이 늘고 소프트 삭제와 엮여 `docs/트러블슈팅.md`가 기록한 것과 같은 종류의 유령 데이터를 만든다. 캐시는 2-14(TTS 콘텐츠 주소화)처럼 **키가 곧 내용인 자리에만** 둔다.

**`drainWaitingQueue`의 "통째로 배정" 동작 변경.** 코드가 "버그가 아니므로 바꾸지 말 것"이라고 명시하고 테스트로 고정해 뒀다. 명세와 팀 합의를 거치기 전에는 건드리지 않는다.

**말랑이 SSE 스트리밍.** 답이 3~4문장으로 짧아서, 1-4(요약 비동기)의 한 줄 변경만으로 체감 개선폭이 스트리밍 도입보다 크고 비용이 훨씬 싸다. 컨트롤러·프런트·프록시 버퍼링까지 손봐야 하는 일을 시연 앞에서 시작할 이유가 없다.

**비전 OCR 페이지 병렬화.** 2-15에 적은 대로 `transcribe`는 CPU 렌더링을 포함한다. 버스터블 인스턴스에서 LiveKit·Postgres와 코어를 다투게 만드는 최적화는 순이익이 마이너스다.

**prod 프로필 게이트에 의존하는 보안 설정.** `SPRING_PROFILES_ACTIVE`가 저장소 어디에도 없고 `application.yml:5`의 기본이 `local`이다. 운영이 local로 뜨고 있을 가능성을 배제할 수 없으므로, 프로필로 켜고 끄는 가드는 **작동을 보장할 수 없다.** 1-9는 값 비교로, 1-10은 nginx로 건다.

**제출 답안의 localStorage 무음 재전송.** 백엔드가 재제출을 `attempt_no`로 보존하는 구조라 유령 시도 행이 남는다. 1-11은 백오프 + 명시적 버튼까지만.

**부하 대비 스케일아웃 작업 전반.** `docs/부하테스트-리포트.md`가 4학급 40명을 안전선으로 실측해 뒀고 시연은 그 범위 안이다. 평상시 부하 0.1 미만인 서버에 용량 작업을 얹는 것보다, 위 1군 6건처럼 **부하와 무관하게 이미 깨져 있는 경로**를 고치는 쪽이 시연 성공 확률을 훨씬 크게 올린다.
