# 트러블슈팅 기록

운영 서버(`classroom.example.com`)를 손보며 마주친 문제들을 남긴다. 증상에서 원인까지
어떻게 좁혀갔는지, 그리고 **틀렸던 판단**까지 함께 적는다. 결과만 적은 기록은
다음에 같은 문제를 만났을 때 도움이 되지 않는다.

---

## 관통하는 패턴 — 소프트 삭제와 DB 제약의 불일치

가장 오래 붙잡은 버그(아래 1번)의 뿌리는 이것이었고, **한 번 알고 나니 같은 구조가
다른 곳에도 숨어 있었다.**

우리는 대부분의 엔티티에 `@SQLRestriction("deleted_at is null")` 을 걸어 **JPA 로 나가는
모든 조회에서 삭제된 행을 자동으로 걸러낸다.** 편리하지만 함정이 있다 —
**DB 의 UNIQUE 제약은 그런 사정을 모른다.** 삭제된 행도 똑같이 자리를 차지한다.

애플리케이션은 "비었다"고 보고, DB 는 "차 있다"고 본다. 그 틈에서 500 이 난다.

alias 문제를 고친 뒤 같은 패턴을 찾아보니, **선생님 가입의 이메일 중복 검사**가
똑같았다. `existsByUsername()` 은 `@SQLRestriction` 에 걸려 탈퇴한 계정을 못 보는데
`users_username_key` 는 삭제된 행까지 덮는다. 탈퇴한 이메일로 재가입하면 친절한 409 가
아니라 500 이 난다. 아직 발현되지 않았을 뿐이었다(삭제된 선생님 계정이 0건).

흥미로운 건 **팀이 이미 이 함정을 학생 아이디 발급에서는 알고 우회하고 있었다**는
점이다. `UserRepository` 에 이런 주석이 있다.

> DB UNIQUE는 soft delete된 행도 포함하므로, @SQLRestriction이 걸리는 JPA 쿼리 대신
> 네이티브로 삭제된 계정까지 세어 번호 재사용(→ UNIQUE 충돌)을 막는다.

한 곳에서 알아챈 함정이 다른 두 곳에는 적용되지 않은 것이다. **패턴을 발견하면
같은 구조를 전수 조사하는 편이 낫다.**

## 1. 학급 생성이 12% 확률로만 성공하던 문제

### 증상

"학급 만들기를 여러 번 눌러야 성공한다." 처음엔 프론트 중복 요청을 의심했다.

### 조사

Nginx 접근 로그에 증상이 그대로 찍혀 있었다.

```
01:13:36 POST /api/classrooms 500
01:13:37 POST /api/classrooms 500
01:13:37 POST /api/classrooms 500
01:13:38 POST /api/classrooms 500
01:13:38 POST /api/classrooms 201   ← 5번째에 성공
```

백엔드 로그의 스택 트레이스가 원인을 가리켰다.

```
duplicate key value violates unique constraint "classroom_alias_key"
Detail: Key (alias)=(bitna) already exists.
```

그런데 코드는 중복을 검사하고 있었다. `AliasGenerator` 가 단어 풀에서 뽑기 전에
`existsByAlias()` 로 확인한다. **확인했는데 왜 중복인가?**

DB 를 직접 보니 답이 나왔다.

```sql
SELECT alias, deleted_at IS NOT NULL AS 삭제됨 FROM classroom WHERE alias='bitna';
-- bitna | t
```

`bitna` 는 **삭제된 학급**이 쥐고 있었다.

### 원인

`Classroom` 엔티티의 `@SQLRestriction("deleted_at is null")` 때문에 `existsByAlias()` 가
삭제된 학급을 보지 못한다. 반면 제약 `classroom_alias_key` 는 `UNIQUE (alias)` — 조건이
없어 삭제된 행까지 덮는다.

숫자로 확인하니 심각했다. 단어 풀 35개 중

| | 개수 |
|---|---|
| 실제로 비어 있음 | **3** |
| 삭제된 학급이 점유(지뢰) | **21** |
| 살아있는 학급이 점유(생성기가 인지) | 11 |

생성기 눈에는 24개가 비어 보이는데 그중 3개만 진짜다. **한 번 누를 때 성공 확률
약 12%**, 평균 8번을 눌러야 한다. 사용자가 겪은 증상과 정확히 맞았다.

### 해결

제약을 부분 유니크 인덱스로 바꿔 **DB 를 엔티티의 관점에 맞췄다.**

```sql
ALTER TABLE classroom DROP CONSTRAINT classroom_alias_key;
CREATE UNIQUE INDEX uq_classroom_alias_live ON classroom (alias) WHERE deleted_at IS NULL;
```

머지 직후 실제 생성이 **첫 시도에 201** 로 성공했고, 그때 배정된 alias 가 `seodam` —
원래 삭제된 학급이 쥐고 있던 지뢰 중 하나였다. 고쳐진 것을 그 자리에서 확인한 셈이다.

### 그 뒤에 한 일

급한 불은 껐지만 구조는 그대로였다. "살아있는 학급마다 전역에서 유일한 단어를 하나씩
점유한다"는 요구가 남아 있어, 학급이 늘면 같은 문제가 다시 온다.

따져보니 **alias 의 유일성은 애초에 필요 없었다.** 진짜 지켜야 하는 건 `username` 의
유일성이고, 그건 발급 시점에 `do/while` 로 이미 보장하고 있었다. 두 학급이 같은
alias 를 써도 한쪽이 `dodam01~05`, 다른 쪽이 `dodam06~10` 을 받는다.

그래서 유일성 요구 자체를 걷어냈다. **코드가 19줄에서 1줄로 줄었다** — 미사용 단어
탐색 루프도, 풀 소진 폴백(`dodam-2`)도, 동시 생성 경합도 전부 사라졌다.

### 배운 것

**"검사했는데 왜 실패하지?" 라는 질문이 나오면, 검사와 강제가 서로 다른 세계를 보고
있는지 의심해야 한다.** 여기서는 애플리케이션 레이어와 DB 레이어였다.

그리고 급한 수정과 구조 수정을 분리한 게 좋았다. 먼저 장애를 멈추고, 그다음에
"이 제약이 정말 필요한가"를 물었다.

## 2. 화면의 시각이 9시간 이르게 표시되던 문제

### 증상

오전 10시 45분에 만든 학급이 화면에 **오전 1시 45분**으로 보였다.

### 조사

먼저 저장값을 의심했지만 DB 는 정상이었다. 확인해보니 서버 전체가 UTC 로 일관됐다 —
호스트, JVM, Postgres 모두 UTC 이고, 시각 컬럼이 전부
`timestamp without time zone` 이라 `timestamptz` 와 섞이지도 않았다.

문제는 **응답이었다.**

```
"2026-08-03T01:45:22"
```

이 문자열에는 "이게 UTC 다"라는 정보가 없다. 그리고 **자바스크립트는 오프셋이 없는
날짜-시간 문자열을 로컬 시간으로 해석한다.** 프론트는 날짜 라이브러리 없이
`new Date(iso).toLocaleTimeString('ko-KR')` 을 쓰고 있었다.

| | |
|---|---|
| 실제 생성 시각 | 8/3 오전 10:45 KST |
| DB 저장값 | `2026-08-03 01:45:22` (UTC, 정상) |
| API 응답 | `"2026-08-03T01:45:22"` (오프셋 없음) |
| 화면 표시 | 오전 1:45 ← 9시간 어긋남 |

### 해결

**서버 타임존을 KST 로 바꾸는 방식은 택하지 않았다.** 컬럼에 오프셋 정보가 없어서,
지금부터 KST 로 넣기 시작하면 어느 행이 UTC 고 어느 행이 KST 인지 영원히 구분할 수
없게 된다. 되돌릴 수 없는 오염이다.

대신 응답에 UTC 임을 명시했다. `LocalDateTime` 을 `"2026-08-03T01:45:22Z"` 로 내보내는
직렬화기를 넣으니 **프론트는 한 줄도 고치지 않고** 정상 표시됐다. 수동 시차 보정을 하는
코드가 없는 것을 먼저 확인해서, 이중 보정될 위험이 없다는 것도 검증했다.

### 배운 것

**"저장이 맞는데 표시가 틀리다"면 경계면을 봐야 한다.** 여기서는 JSON 직렬화였다.

그리고 되돌릴 수 없는 선택지(서버 타임존 변경)와 되돌릴 수 있는 선택지(응답 형식 변경)가
있을 때는 후자를 고른다. 데이터가 섞이면 복구할 방법이 없다.

한 가지 더. 배선 테스트를 따로 뒀다 — `@JsonTest` 로 **스프링이 실제로 이 직렬화기를
등록했는지** 확인한다. 로직이 맞아도 스캔이 안 되면 응답은 그대로이기 때문에, 단위
테스트만으로는 "동작한다"고 말할 수 없었다.

## 3. 수업이 영원히 끝나지 않던 문제

### 증상

`live_session` 중 `ended_at IS NULL` 인 행이 14개. 가장 오래된 것은 **8일째**였다.
참가자는 모두 나갔는데 세션만 열려 있었다.

### 조사

LiveKit 은 방이 비면 `empty_timeout`(기본 5분) 후 `room_finished` 웹훅을 보낸다.
로그를 세어보니 **실제로 154번 보냈다.**

그런데 백엔드가 그걸 처리한 흔적이 없었다. 웹훅 컨트롤러 첫 줄이 범인이었다.

```java
if (type == null || room == null || participant == null) {
    return;
}
```

**`room_finished` 에는 `participant` 필드가 없다.** 방이 닫힌 사건이지 특정 참가자의
사건이 아니기 때문이다. 실제 페이로드를 확인하니 `event` 와 `room` 뿐이었다.

그래서 154번의 이벤트가 전부 이 한 줄에서 조용히 버려졌다.

### 원인

수업은 선생님이 "수업 종료"를 **명시적으로 누를 때만** 닫혔다. 브라우저를 그냥 닫으면
영원히 열린 채로 남는다. 실제 종료 API 호출은 로그 전체에서 11건, 생성된 세션은 24개였다.

### 해결

`participant` 가 필요한 이벤트에만 검사를 적용하도록 순서를 바꾸고, 메인 룸
(`session-N`)의 `room_finished` 를 받아 수업을 종료한다.

**팀 룸(`session-N-team-M`)은 무시해야 한다.** 순회 중 팀 방이 닫히는 건 흔한 일이라,
구분하지 않으면 팀을 옮길 때마다 수업이 끝나버린다. 이 함정을 테스트로 고정했다.

이미 쌓인 14개는 마이그레이션으로 정리하되, **마지막 활동으로부터 6시간이 지난 것만**
닫았다. 지금 진행 중일 수도 있는 수업을 배포가 끊으면 안 되기 때문이다. `ended_at` 은
`now()` 가 아니라 마지막 참가자 활동 시각으로 채웠다 — `now()` 로 채우면 8일짜리
수업이 이력에 남아 통계가 왜곡된다.

남겨둔 3개는 이후 방이 닫히면서 **새 웹훅 경로가 자동으로 종료**했다. 고친 것이
동작한다는 증거가 됐다.

### 배운 것

**조용히 버려지는 경로를 조심해야 한다.** 이 가드는 `return` 만 하고 로그도 남기지
않았다. 154번의 이벤트가 사라지는 동안 아무 신호가 없었다.

가드를 쓸 때는 "이 조건에 걸리는 정상적인 입력이 있는가"를 물어야 한다.

## 4. 빌드가 깨졌는데 서비스는 멀쩡했던 날

### 배경

기존 배포는 이랬다.

```bash
docker stop mallang-backend
docker rm mallang-backend
docker run -d --name mallang-backend ... mallang-backend:latest
```

**먼저 죽이고 나서 새로 띄운다.** 매 배포마다 스프링 기동 시간만큼 502 가 나고,
새 컨테이너가 기동에 실패하면 **돌아갈 컨테이너가 이미 없다.**

그래서 블루-그린으로 바꿨다. 슬롯을 blue(8081)/green(8082) 둘로 나누고, 놀고 있는
쪽에 새 버전을 띄운 뒤 **헬스체크를 통과한 뒤에만** Nginx 트래픽을 넘긴다.
통과하지 못하면 전환이 아예 일어나지 않으므로 롤백할 것이 없다.

### 그날 일어난 일

세션 자동 종료(3번)를 머지했더니 빌드가 **실패**했다.

```
MigrationVersionTest > 마이그레이션 버전 번호는 중복되지 않는다 FAILED
```

브랜치를 딴 뒤 팀에서 `V18__ai_tutor_memory` 와 `V19` 를 먼저 머지했는데, 번호를 다시
확인하지 않고 `V18` 로 낸 것이 원인이었다. **내 실수다.**

그런데 **서비스는 200 을 유지했다.** 빌드 단계에서 막혀 배포에 도달하지 못했고,
기존 슬롯이 계속 서빙했다. 예전 구조였다면 컨테이너를 이미 지운 뒤였을 것이다.

`V20` 으로 옮겨 재배포해서 복구했다.

### 배운 것

**무중단 배포의 값어치는 평상시가 아니라 사고 났을 때 드러난다.** 도입한 당일에
그 값어치를 확인하게 될 줄은 몰랐다.

그리고 **마이그레이션 번호는 브랜치를 딸 때가 아니라 MR 을 올리기 직전에 확인해야
한다.** 팀이 병렬로 작업하면 그 사이에 번호가 늘어난다. 다행히 팀에 이미
`MigrationVersionTest` 라는 중복 감시 장치가 있어 CI 가 잡아줬다.

## 5. TURN 을 켜다가 LiveKit 을 내린 일

### 배경

WebRTC 연결이 지금까지 1,179건 전부 UDP 직접 연결로 성공했다. 그런데 **접속자가 전부
같은 네트워크(`211.192.210.x`)** 였다. UDP 가 열린 환경에서만 검증됐다는 뜻이다.

초등학교 대상 서비스라 교육청 망·학교 와이파이에서 접속하게 되는데, UDP
50000-50999 가 막히면 TCP 7881 로 폴백하지만 비표준 포트라 함께 막히는 경우가 많다.
그래서 TLS TURN(5349)을 켜기로 했다.

### 일어난 일

머지 후 배포가 돌았고 LiveKit 이 **재시작 루프**에 빠졌다.

```
TURN tls cert required: open /etc/letsencrypt/live/.../fullchain.pem: no such file or directory
```

Jenkins 의 LiveKit 배포 단계는 이것뿐이다.

```bash
cp infra/server/livekit/livekit.yaml /deploy/livekit/livekit.yaml
docker restart mallang-livekit
```

**`docker restart` 는 볼륨 마운트를 바꾸지 않는다.** 설정 파일은 새것으로 바뀌었는데
인증서를 넣어줄 마운트가 없으니, 있지도 않은 파일을 찾다가 죽은 것이다.

컨테이너를 재생성(`docker compose up -d --force-recreate livekit`)해서 복구했다.

### 사고를 줄인 것

**자정에 작업했고, 머지 직전에 진행 중인 수업이 0건인 것을 확인했다.** 실사용자
영향은 없었다. 커밋 메시지에 "머지 후 재생성이 필요하다"고 미리 적어둔 것도
복구를 빠르게 했다.

### 배운 것

**설정 변경과 컨테이너 스펙 변경은 배포 경로가 다르다.** 파일 내용만 바뀌면 재시작으로
충분하지만, 마운트·포트·환경변수가 바뀌면 재생성이 필요하다. 배포 스크립트가
어느 쪽을 하는지 알고 있어야 한다.

그리고 **위험한 작업은 사용자가 없는 시간에 한다.** 당연한 말인데, 확인하는 습관이
있느냐가 차이를 만든다.

### 덤으로 알게 된 것

TURN 은 시그널(TCP 5349) 말고 **릴레이용 UDP 30000-40000** 도 쓴다. 격리된 컨테이너로
미리 기동해보고 로그의 `relay_range_start/end` 에서 알았다. 이걸 안 열었으면
**TLS 연결은 되는데 영상만 안 흐르는** 골치 아픈 상태가 됐을 것이다.

## 6. 측정 도구가 거짓말한 세 번

문제를 조사하려고 도구를 붙였는데, 그 도구가 틀린 답을 준 경우들이다.

### cAdvisor 가 컨테이너를 못 본다

컨테이너별 자원을 보려고 붙였는데 모든 컨테이너에서 실패했다.

```
failed to identify the read-write layer ID
open /rootfs/var/lib/docker/image/overlayfs/layerdb/mounts/...: no such file or directory
```

이 서버의 Docker 는 **containerd 스냅샷터**(`Storage Driver: overlayfs`,
`io.containerd.snapshotter.v1`)를 쓴다. cAdvisor 의 Docker 연동은 구형 그래프 드라이버
배치를 전제하는데, `/var/lib/docker/image/` 자체가 존재하지 않는다.

containerd 를 직접 보게 하니 수집은 됐지만 `name` 라벨이 **컨테이너 이름이 아니라
64자 ID 해시**로 붙었다. 대시보드에 해시가 찍히고 배포마다 새 ID 가 쌓인다.

**그래서 뺐다.** 반쯤 동작하는 걸 남겨두면 나중에 누군가 그 숫자를 믿는다. 대신
왜 뺐는지를 README 에 적어 같은 길을 되짚지 않게 했다.

### node_exporter 가 자기 자신의 네트워크를 본다

부하 테스트 후 "네트워크가 병목이었나" 확인하려는데 **수신·송신이 0 MB/s** 로 나왔다.
100 Mbps 를 쓴 직후인데 0 일 리가 없다.

원인은 node_exporter 가 host 네트워크가 아니라 자기 컨테이너의 인터페이스(`eth0`, `lo`)를
보고 있던 것. 호스트의 실제 랜카드는 `enX0` 다.

`network_mode: host` 로 바꾸니 이번엔 Prometheus 가 못 긁었다. 리슨 주소를 `127.0.0.1`
로 묶어서 컨테이너에서 닿지 않았고, 전체 인터페이스로 바꾸니 이번엔 **ufw 가
컨테이너→호스트 트래픽을 막았다.** 도커 대역(`172.16.0.0/12`)만 열어 해결했다.

### 부하 테스트 안전장치가 자기 자신을 오인한다

부하 테스트 스크립트에 "진행 중인 수업이 있으면 멈춘다"는 안전장치를 넣었다.
그런데 두 번째 실행이 **무한 대기**에 빠졌다.

직전 테스트가 남긴 참가자 접속을 "실제 수업"으로 센 것이다. 게다가 확인 프롬프트가
`read` 라, 비대화형 실행에서는 입력이 올 수 없어 영원히 멈췄다.

두 가지를 고쳤다. `loadtest-` 룸의 접속은 집계에서 빼고, **비대화형에서는 프롬프트
대신 실패**하도록 했다(강행은 `LOADTEST_FORCE=1`).

### 배운 것

**측정 도구를 붙였으면 그 도구가 맞는 값을 주는지부터 확인해야 한다.** 0 이라는 숫자가
"부하가 없었다"인지 "측정이 안 됐다"인지 구분하지 못하면, 그 지표는 없느니만 못하다.

그리고 **확인을 요구하는 안전장치는 확인을 받을 수 없는 환경을 반드시 고려해야 한다.**
멈추는 것과 막는 것은 다르다. 닫힌 쪽으로 실패시켜야 한다.

## 전체를 통해 남는 것

**증상이 아니라 증거를 따라간다.** "여러 번 눌러야 된다"는 막연한 증상이
접근 로그의 `500 500 500 500 201` 로, 다시 스택 트레이스로, 다시 `SELECT` 한 줄로
좁혀졌다. 각 단계에서 추측 대신 확인할 수 있는 것을 확인했다.

**고치기 전에 왜 그렇게 되어 있는지 묻는다.** alias 유일성은 제약을 고치는 것으로
끝낼 수도 있었지만, "이 제약이 정말 필요한가"를 물었더니 코드가 19줄에서 1줄로 줄었다.

**되돌릴 수 있는 선택지를 고른다.** 서버 타임존 변경은 데이터를 영구히 오염시키지만
응답 형식 변경은 언제든 되돌릴 수 있다.

**안전장치는 사고가 나야 값어치가 보인다.** 블루-그린은 도입 당일 내 실수를 막아줬고,
백업은 아직 쓸 일이 없었지만 없었다면 사고 때 복구 수단이 없었다.

**내가 만든 것도 의심한다.** 이 기록의 6번은 전부 내가 붙인 도구가 틀린 답을 준
경우다. 도구를 믿기 전에 검증하는 습관이 결국 시간을 아꼈다.
