1. 이미지 — 이게 병목이었다

디자인 자산이 전부 PNG 로 들어와 있었다. 배경 일러스트 한 장이 2 MB 를 넘는 것도 있었고, /login 의 LCP 요소가 정확히 그중 하나였다.

  • 1차 (08-02) — PNG 38 장을 WebP 로 일괄 변환. 22.1 MB → 1.04 MB (−95.3%).
  • 2차 (08-07) — 변환 이후에도 새 자산이 다시 PNG 로 들어와 9 장 8.4 MB 가 쌓여 있었다. 코드가 실제로 참조하는 2 장만 WebP 로 바꾸고(1.5 MB → 85 KB), 아무도 참조하지 않는 7 장 6.7 MB 는 지웠다. public/assets 기준 9.8 MB → 3.2 MB.

변환은 원본 해상도를 유지하고 품질을 실측해서 정했다. 재인코딩한 배경 한 장은 785 KB → 30 KB 인데 PSNR 48.7 dB · 채널 평균오차 0.65/255 로 육안 차이가 없는 범위다. “줄었다”만 보고 화질을 버리면 디자인 기준(ref/ 1:1 재현)을 어기게 된다.

지우는 쪽도 src/ 만 보면 안 된다. 앱이 더는 안 쓰는 PNG 2 장을 디자인 원본 ref/teacher.html 이 참조하고 있어서 남겼다.

2. 폰트

index.html 이 Noto Sans KR(4 weight)과 Pretendard 를 둘 다 받고 있었다. 그런데 --font-sans 가 'Pretendard', 'Noto Sans KR', … 라서 Pretendard 가 뜨는 순간 Noto 는 절대 쓰이지 않는다. 쓰지도 않을 한 벌을 받느라 첫 화면이 늦어지고 있었다.

  • Google Fonts 제거 → 외부 origin 2 개에서 1 개로.
  • Pretendard 를 static → variable dynamic-subset 으로 교체. unicode-range 로 잘게 나뉘어 화면에 실제로 나온 글자의 조각만 받는다. 글자 수가 한정된 초등 교실 화면에서 효과가 크다.
  • 08-07 — 남아 있던 렌더 블로킹을 없앴다. 이 CSS 는 60 KB · @font-face 92 개라 받아 파싱할 때까지 첫 그림이 안 그려졌다. preload as="style" 로 우선순위를 올리고 media="print" + onload 로 적용 시점만 뒤로 미뤘다. Pretendard CSS 자체가 font-display: swap 이라 글자가 안 보이는 구간은 생기지 않는다.

여기서 한 번 넘어졌다. dynamic-subset 이 선언하는 family 이름은 'Pretendard Variable' 이다. 'Pretendard' 만 적어두면 웹폰트가 떠도 매칭되지 않아 조용히 시스템 글꼴로 떨어진다. 화면이 깨지지 않아 한참 못 알아챘다.

4. 재배포 때 다시 받는 양

5. 이미지 요소의 자리 예약

<img> 32 개 중 width/height 를 가진 것이 1 개뿐이었다. 받기 전에는 높이가 0 이라 그림이 도착할 때마다 아래 내용이 밀린다. 32 개 전부에 decoding="async", 목록 행 아바타 4 곳에 loading="lazy", 비율이 확정되는 13 곳에 실제 자연 크기를 넣었다.

크기가 제각각인 동적 소스(학급 카드 sj_1~6, 학생 아바타 SM_CHARS, 학년 새싹)에는 일부러 넣지 않았다. 한 값으로 박으면 CSS 가 한 축만 정한 이미지가 찌그러진다. 넣은 13 곳은 스크립트로 실제 파일 크기와 전수 대조했다. 학급 카드에는 loading="lazy" 도 걸지 않았다 — 로그인 직후 첫 화면의 주 콘텐츠라 늦게 받으면 LCP 가 밀린다.

사용자 체감은 어떻게 달라지나

실행 환경(학교 와이파이 + 노후 PC)을 기준으로 위 수치를 해석하면 이렇다.

  • 첫 진입에서 하얀 화면이 사라졌다. LCP 3.1 초는 아이가 “안 켜져요”라고 말하기 시작하는 구간이다. 0.97 초면 누르자마자 반응한 것으로 읽힌다.
  • 글자가 늦게 바뀌는 현상이 줄었다. 안 쓰는 폰트 한 벌을 걷어내고 실제로 쓰인 글자 조각만 받으므로, 시스템 글꼴로 먼저 그려졌다가 교체되기까지의 시간이 짧다.
  • 느린 기기에서 첫 조작이 덜 밀린다. 로그인 화면에서 WebRTC 클라이언트를 파싱하던 것을 없앴다. 다운로드보다 파싱·컴파일 비용이라 CPU 가 느릴수록 차이가 커진다.
  • 화면이 뜨면서 내용이 튀는 일이 줄었다. 이미지 자리를 미리 잡아 두어 그림이 도착할 때 아래 버튼이 밀려 내려가지 않는다 — 누르려던 것을 잘못 누르는 상황이 준다.
  • 수업 중 배포가 나가도 다시 받는 양이 절반. React · 모션 · PDF 라이브러리는 캐시에 남는다.

남은 것

  • LiveKit 청크(127 KB gzip)가 앱 코드를 고칠 때마다 해시가 바뀌어 재발급된다. 벤더로 고정하면 재다운로드가 더 줄어든다 — 측정만 해두고 아직 적용하지 않았다.
  • nginx 가 gzip 만 쓴다. brotli 를 켜면 JS 에서 보통 15~20% 더 줄어든다. 서버 설정이라 프론트 범위 밖.
  • Pretendard self-host 로 외부 origin 을 완전히 없앨 수 있다. woff2 조각이 92 개라 저장소에 넣는 비용과 견줘 보류했다.

02트러블슈팅

가장 많이 만난 실패는 크래시가 아니라 “정상처럼 보이는데 아무것도 전달되지 않는” 상태였다. 사용자가 초등학생이라 정확히 신고해 주지 못한다는 점이 진단을 어렵게 만들었다. 아래 세 건은 전부 화면상으로는 멀쩡했다.

케이스 1 — StrictMode 이중 마운트가 LiveKit 접속을 영구히 죽였다. 선생님만.

LiveKit 내 작업 ae9221d services/signaling/ClassroomSignaling.ts

증상

선생님 화면은 로컬 미리보기라 정상으로 보이는데, 학생에게는 영상이 전혀 가지 않는다. 그 페이지에 머무는 동안 절대 복구되지 않는다. 학생 계정으로는 재현되지 않았다.

원인

가드의 순서 문제였다. StrictMode 의 첫 마운트가 티켓 발급 (POST /sessions/{id}/join) HTTP 왕복을 기다리는 사이 cleanup 이 돌아 leaving=true · ticket=null 이 된다. 두 번째 마운트가 들어올 때 opening 이 아직 true 라 if (this.room || this.opening) return 에 걸려 즉시 반환된다. 결과적으로 ticket 이 영구히 null 이 되어 open() 도 scheduleReconnect() 도 못 한다 — 재접속 경로가 통째로 사라진다.

“왜 선생님만인가”가 결정적 단서였다. 학생 훅은 join 을 connectWithTicket 앞에서 await 해 cleanup 시점에 opening === false 다. 선생님 훅만 티켓 발급이 콜백 안에 있어서 이 좁은 창에 정확히 걸렸다.

해결

ticket · leaving · retries 세팅을 가드보다 먼저 옮겼다. 그러면 진행 중이던 open() 이 if (this.leaving) return 을 통과해 접속을 끝낸다.

개발 모드에서만 나는 문제가 아니다. StrictMode 는 이 경합을 확실하게 재현시켰을 뿐이고, 같은 창은 빠른 화면 전환에서도 열린다.

케이스 2 — 선생님이 친 동그라미가 학생 화면에서는 다른 자리에 찍혔다

판서 · 좌표계 내 작업 services/media/ScreenAnnotator.ts hooks/useScreenAnnotation.ts

증상

선생님이 화면공유 위 단어에 동그라미를 치면 학생 화면에서는 위치가 밀려서 찍혔다. 획이 안 가는 게 아니라 엉뚱한 데 갔다. 어긋나는 정도는 공유하는 창의 모양에 따라 달랐고, 어떤 날은 거의 맞아서 재현이 들쭉날쭉했다.

원인

좌표는 처음부터 0~1 로 정규화해 보내고 있었다. 문제는 무엇을 기준으로 나누느냐였다. 선생님 슬라이드(가로로 넓음)와 학생 방송 카드(16:10)는 캔버스 모양이 다르다. 각자 자기 캔버스를 기준으로 나누면 같은 0.5 가 서로 다른 지점을 가리킨다.

그래서 양쪽 캔버스 안에 같은 비율의 논리 보드를 letterbox 로 잡고 그 안에서만 좌표를 주고받도록 설계해 뒀는데, 그 기준 비율이 16/10 고정값이었다. 실제 배경 영상은 화면공유 원본 비율(16:9 · 4:3 · 세로 등)대로 object-contain 되므로 보드 박스와 영상 박스가 어긋났다. 공유 창이 우연히 16:10 에 가까우면 맞아 보였다 — 재현이 들쭉날쭉했던 이유다.

해결

기준 비율을 고정값에서 배경 영상의 실제 비율 (videoWidth / videoHeight)로 바꿨다. 같은 트랙을 양쪽이 함께 보므로 이 값은 두 화면에서 반드시 같다. 메타데이터가 아직 없으면 기존 고정값으로 폴백하고, loadedmetadata · resize 에서 이미 그린 획을 새 박스로 다시 그린다.

기준 영상은 호출부가 setBackgroundVideo() 로 명시해 넣는다. 이전에는 캔버스 부모의 <video> 를 엔진이 스스로 찾았는데, 한 화면에 선생님 방송과 학생 셀프뷰가 섞여 있어 DOM 구조가 바뀌면 조용히 엉뚱한 영상을 기준으로 삼았다.

카메라 영상은 object-cover 라 컨테이너 모양대로 잘리므로 어떤 기준을 써도 정확히 맞출 수 없다. 판서는 화면공유 위에서 쓰는 기능이라 공유 기준으로 맞추기로 결정하고 그 사실을 주석에 남겼다.

케이스 3 — 화면공유가 안 나가거나, 얼어붙은 마지막 프레임에 묶였다

LiveKit 내 작업 ae9221d hooks/useTeacherMedia.ts

증상

세 가지로 신고가 들어왔다.

  • 접속이 끝나기 전에 켠 화면공유가 영원히 안 나간다.
  • 재접속 후 버튼은 “공유 중지”인데 학생에게는 아무것도 안 온다.
  • 브라우저 기본 UI 로 공유를 멈추면 학생 화면이 얼어붙은 마지막 프레임에 묶이고, 그 뒤 선생님이 카메라를 켜도 바뀌지 않는다.

원인

게시가 toggleScreenShare 안에서만 일어나는 명령형 구조가 근본 원인이었다. “버튼을 누른 그 순간”에만 게시를 시도하므로, 그 순간 조건이 안 맞거나 나중에 조건이 바뀌면 따라갈 방법이 없다.

  • publishScreen 이 if (!room) return 으로 조용히 버렸다 — 카메라에는 publishIfReady 가 있었는데 공유에는 없었다.
  • 재접속으로 Room 인스턴스가 새로 생겨도 재게시를 걸어 줄 트리거가 없었다.
  • 브라우저 UI 로 멈추면 로컬만 정리하고 unpublish 를 안 불러 LiveKit publication 이 죽은 트랙을 물고 남았다. 학생 화면은 화면공유를 카메라보다 우선 표시하므로 거기에 묶인다.

해결

명령형을 선언형으로 뒤집었다. [signalingStatus === 'connected' && screenSharing] 을 상태로 보고 단일 effect 에서만 publish/unpublish 하게 하고, toggleScreenShare 는 화면 획득 · 중지만 담당하게 했다. 연결이 끊기면 screenPublishedRef 를 리셋한다 — 이전 Room 의 publication 은 이미 죽은 것이므로.

같은 계열의 문제가 나중에 한 번 더 나왔다. 방송이 화면 밖에서 살아남게 된 뒤, 수업 화면에 돌아오면 PDF 발표가 켜진 채로 검게 나왔다. “무엇을 게시했는가”를 컴포넌트가 useRef 로 들고 있어서 다시 마운트되면 기억이 초기화되고, 이미 게시 중인데도 재게시한 것이다. LiveKit 은 게시를 내릴 때 원본 트랙까지 정지시킨다 (stopLocalTrackOnUnpublish 기본값 true) — 그 순간 PDF 캔버스 캡처 트랙이 죽는다. 게시 기억을 방송 객체로 옮기고 stopOnUnpublish=false 를 주는 것으로 해결했다. (수정: 오현우 · c5c2ef9)

03측정 방법

최적화 이전의 측정값을 남겨두지 않았다. 그래서 “전/후”를 만들려면 과거를 복원해야 했다. 각 시점의 커밋을 git worktree 로 꺼내 다시 빌드하고, 같은 Chrome 인스턴스에서 Lighthouse 를 3 회씩 돌려 중위값을 썼다. 이미지 크기는 git ls-tree -r -l 로 커밋 간 직접 비교라 추정치가 아니다.

  • 엔트리 청크 분해 — vite build --sourcemap 후 소스맵의 sourcesContent 를 패키지별로 합산했다. “엔트리의 82%가 livekit”이라는 사실은 이 방법으로 나왔다.
  • 재다운로드량 — 같은 소스를 설정만 바꿔 빌드하고, 페이지 컴포넌트의 문자열 한 곳을 고쳐 다시 빌드해서 파일명(콘텐츠 해시)이 바뀐 .js / .css 의 합계를 셌다.
  • 이미지 화질 — 재인코딩 결과를 다시 디코딩해 원본과 픽셀 단위로 비교했다 (PSNR · 평균절대오차).
  • 지연 로딩 확인 — 빌드 산출물 검사만으로는 부족해서, 실제로 로그인 화면을 띄우고 performance.getEntriesByType('resource') 로 livekit 모듈 요청이 0 건인지 확인했다.

주의해서 읽어야 하는 구간이 있다. 스플리팅 도입과 WebP 변환 사이에는 이틀치 기능 추가가 섞여 있다. 그 구간의 JS 증가는 최적화가 실패한 게 아니라 코드가 늘어난 것이다.

또 npm run dev 에서 잰 Lighthouse 는 55 점이 나오는데 이 숫자는 의미가 없다 — dev 서버는 미니파이 · 번들링 없이 모듈을 수백 개로 쪼개 내려준다. 이 문서의 값은 전부 프로덕션 빌드 기준이다.
