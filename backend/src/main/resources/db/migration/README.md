# 마이그레이션 규칙

## 이미 적용된 파일은 한 글자도 고치지 않는다

Flyway 는 파일 내용의 체크섬을 `flyway_schema_history` 에 적어 두고, 기동할 때마다 대조한다.
운영 DB 에 이미 적용된 파일을 나중에 고치면 — **주석 한 줄이라도** — 검증에 실패하고
애플리케이션이 아예 뜨지 못한다.

```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 26
-> Applied to database : 1318044310
-> Resolved locally    : 259828752
```

실제로 2026-08-05 에 이 일이 있었다. 파일을 `V24→V26`, `V25→V27` 로 번호만 옮기면서
파일 안의 `-- V24:` 주석도 함께 고쳤는데, 그 두 마이그레이션은 이미 운영 DB 에 적용된
뒤였다. 그때부터 **백엔드 배포가 전부 실패**했다 — 새 슬롯이 기동하지 못해 블루-그린
전환이 막혔고, 헬스체크 실패로 CI 가 중단됐다.

그래서 `V26__assignment_subject_hanja_to_korean.sql` 의 첫 줄은 `-- V24:`,
`V27__report_card.sql` 의 첫 줄은 `-- V25:` 로 남아 있다. **파일명과 어긋나 보이지만
고치지 말 것.** 적용 당시의 바이트를 그대로 지켜야 체크섬이 맞는다.

## 번호를 바꿔야 한다면

아직 **어디에도 적용되지 않은** 마이그레이션만 번호를 바꿀 수 있다. 운영에 한 번이라도
나갔다면 그 파일은 동결이다. 바꾸고 싶은 내용이 있으면 새 버전을 추가한다.

```
V30__무엇을_한다.sql        ← 새 파일로 추가
```

## 이미 어긋났다면

SQL 이 바뀌지 않았고 주석 등 무해한 차이뿐이라면 두 가지 길이 있다.

1. **파일을 적용 당시 내용으로 되돌린다** (권장 — DB 를 건드리지 않는다)
   ```
   git show <바꾸기_전_커밋>:경로/V26__....sql > 경로/V26__....sql
   ```
2. `flyway repair` 로 이력의 체크섬을 현재 파일에 맞춘다. DB 를 쓰므로 이력 테이블을
   먼저 백업할 것.

**SQL 자체가 바뀌었다면 둘 다 위험하다.** DB 에는 옛 SQL 이 적용돼 있는데 코드는 새 SQL 을
기대하게 되어, 스키마와 엔티티가 조용히 어긋난다. 그때는 차이를 새 마이그레이션으로 따로
적용해야 한다.
